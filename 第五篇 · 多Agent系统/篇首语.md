# 第五篇 · 多 Agent 系统

> **"一个 Agent 是工具，一群 Agent 是组织。"**

---

你雇了一个全能型员工——他能写代码、能做设计、能跑运维、能写文档。你给他一个人的工资，指望他干五个人的活。

结果呢？他每件事都做得"还行"，但没有一件事做得"极好"。你让他写代码时，脑子里还挂着昨天那个运维工单没关；你让他做设计时，他满脑子是上次的 bug 修复思路。不是他不努力——是**一个人的注意力带宽有上限**。

你真正需要的是一支团队：前端专家专注前端、后端专家专注后端、运维专家专注运维、QA 专家专注测试。每个人在自己的领域深钻，通过协作完成整体目标。

**多 Agent 系统就是 AI 的团队化。**

一个 Agent 再强大，它终究是一个模型在一个上下文窗口里做推理。上下文越长，注意力越分散（我们在第 13 章见过 Context Rot）；角色越多，推理质量越下降。当你试图用一个 Agent 同时扮演"需求分析师 + 编码者 + 测试员 + 审查员"时，它就像那个全能型员工——每件事都"还行"，没有一件事"极好"。

多 Agent 系统的核心思想是**专业化分工**：把一个复杂任务拆分给多个专门化的 Agent，每个 Agent 在自己狭窄的领域里做到最好，通过通信协议协作完成整体目标。这和人类社会几千年的组织进化方向完全一致——从"万能工匠"到"专业分工"。

但多 Agent 不是银弹。Agent 多了，新的工程问题随之而来：

- **通信开销**：Agent 之间传递信息需要消耗 Token，5 个 Agent 的协作成本可能是单 Agent 的 3-5 倍
- **协调复杂度**：谁先做？谁后做？结果冲突怎么办？一个 Agent 的幻觉会不会传染给其他 Agent？
- **故障归因**：4 个 Agent 跑完一条链路，输出是错的——哪个 Agent 出了问题？在 20 步推理链里定位故障，比单 Agent 调试难一个数量级
- **成本乘法**：如果每个 Agent 90% 正确，4 个串联的端到端正确率只有 0.9⁴ ≈ 65.6%——质量不会累加，只会乘法式衰减

这些工程问题的答案，就是本篇四章的主题。

**第 17 章**讲多 Agent 的三大架构模式——Supervisor（中央调度）、Network（对等协作）、Hierarchical（分层委派），以及"什么时候该上多 Agent，什么时候单 Agent 就够"的决策边界。

**第 18 章**讲 Agent 通信协议——MCP 解决"Agent → 工具"的纵向通信（第三篇已深入展开），A2A 解决"Agent → Agent"的横向通信。2025 年 4 月 Google 推出 A2A 协议，2026 年 3 月发布 v1.0 稳定版，150+ 组织支持，成为 Agent 间协作的事实标准。这一章深入 A2A 的四大核心概念（Agent Card / Task / Message / Artifact）、Task 生命周期、通信流程实战和安全风险防御。

**第 19 章**讲多 Agent 协作策略——任务怎么分解、结果怎么聚合、冲突怎么处理、消息怎么设计。

**第 20 章**讲多 Agent 框架实战——LangGraph、CrewAI、OpenAI Swarm、AutoGen 四大框架的对比与选型。

> **比喻：从个体户到公司制。**

> 单 Agent 是个体户——一个人包揽所有活，灵活但天花板低。多 Agent 是公司制——分工明确、流程清晰、规模可扩展，但管理成本上来了。

> 关键转变在于：你不再只是"写一个 Agent"，而是在"设计一个组织"。组织的架构、通信、协调机制——这些人类社会几千年摸索出来的管理智慧，正在被 Agent 工程重新发现。
