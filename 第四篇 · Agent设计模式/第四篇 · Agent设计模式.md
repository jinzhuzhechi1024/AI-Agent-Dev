# 第四篇 · Agent 设计模式 —— 可复用的智能体架构

> **篇首语：模式比框架长寿——LangChain 会迭代，但"路由模式""并行模式"会长期存在**

---

你大概经历过这样的场景：团队花了两周用 LangChain 0.1 搭了一个 Agent，下个月 LangChain 0.2 发布，API 全变了，代码推倒重来。又过了半年，CrewAI 火了，技术负责人说"我们换框架吧"。你看着自己写的几千行代码，叹了口气。

这不是个别现象。2023 年至今，Agent 框架经历了至少三轮大洗牌：LangChain → LangGraph → CrewAI/AutoGen → OpenAI Agents SDK。每一轮都伴随着 API 重构、概念重命名、最佳实践推翻。开发者疲于追框架，却忽略了框架背后的东西。

**框架是交通工具，模式是地图。**

交通工具会换代——马车变成汽车，汽车变成无人驾驶车——但从北京到上海的方向不会变。同理，LangChain 的 `RunnableLambda` 可能被淘汰，但"把任务拆成顺序步骤，每步一个 LLM 调用"这个思路不会变；CrewAI 的 `Crew` 类可能改名，但"给不同 Agent 分配不同角色，协同完成任务"这个架构不会变。

前者叫**框架**，后者叫**模式**。

2024 年 12 月，Anthropic 的工程师 Erik Schluntz 和 Barry Zhang 发表了一篇不到 10 页的博客文章——《Building Effective Agents》。这篇文章没有推荐任何框架，没有贴任何库的安装命令，只是冷静地列出了五种"工作流模式"和一种"自主 Agent 模式"。文章发布后在 Hacker News 拿下 763 分，被翻译成十几种语言，成为 Agent 领域被引用最多的工程文献之一。

它为什么火？因为它回答了一个所有人都在问的问题：**撇开框架，Agent 的本质架构到底是什么？**

答案是：一组可组合的**设计模式**。

本篇要做的事情，和 Anthropic 那篇文章一脉相承，但更进一步。我们将从三个维度展开：

**第一，分类体系。** Anthropic 给出了五种工作流模式，但真实世界的 Agent 系统远不止五种。学术界和工业界陆续提出了 20 多种模式——反思（Reflection）、规划（Planning）、辩论（Debate）、熔断（Circuit Breaker）……我们需要一个分类框架，把它们组织成一张可导航的地图，而不是一锅乱炖。本篇提出**四象限分类法**：流程控制、增强优化、交互协作、稳健安全。

**第二，模式详解。** 每种模式不是一句话定义就能用好的。路由模式看似简单——"分类然后分发"——但分类器用什么模型？错了怎么办？延迟能接受吗？本篇会逐个拆解每种模式的内部结构、适用场景、失败模式和工程实现要点。

**第三，模式组合。** 真实系统从来不是单一模式。一个客服 Agent 可能是"路由 → 提示链 → 评估器-优化器"的组合；一个代码 Agent 可能是"编排者-执行者 + 反思 + 护栏"的组合。模式之间的可组合性，才是 Agent 架构设计的精髓。

> **比喻：设计模式是菜谱。**

> 菜谱告诉你"红烧肉先焯水再炒糖色"，但不规定你必须用铁锅还是砂锅。你可以用电饭煲做红烧肉（虽然味道差点），但不能跳过焯水直接炖——那是物理规律，不是工具偏好。

> Agent 设计模式同理。"路由模式"告诉你"先分类再分发"，但不规定你用 LangGraph 的条件边还是手写 `if-else`。你可以用任何框架实现路由，但不能跳过分类直接处理所有输入——那是架构规律，不是框架偏好。

本篇共三章：

- **第 14 章 模式总览**：为什么需要设计模式，四象限分类框架，模式选择决策树
- **第 15 章 流程控制与增强优化模式**：五种 Anthropic 工作流模式 + 四种增强模式 + 模式组合实战
- **第 16 章 交互协作与稳健安全模式**：人机协作/委派/辩论/共识/交接 + 异常处理/护栏/降级/熔断/限流

读完本篇，你将拥有一个跨越框架更迭的架构设计工具箱。当下一个 Agent 框架出现时，你不需要从头学起——你只需要问：**它实现了哪些模式？哪些模式它还没实现？**
